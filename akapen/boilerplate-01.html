packages はフラットに並べ、カウンターの保存先はアプリ側で差し替える

結論: apps/ に 2 アプリ、packages/ に counter・ui-components・datastore-indexed-db・datastore-memory を同じ階層で置きます (Kysely / Atlas 用の database は問 2 次第)。カウンター本体は「読み書きできる保存先」の型だけを自分で宣言し、どの保存先を渡すかはアプリが決めます。手順書は docs/setup/ に工程ごとに分けて書き、その手順書のコマンドを実際に打ってリポジトリを作ります。
このシートで使う言葉: 注入 = アプリ起動時に、カウンター本体へ「IndexedDB 版」か「メモリ版」の保存先を渡すこと。依存の向き = どのパッケージがどれを import してよいか。逆向きの import を eslint でエラーにする。生成コマンド = create-next-app や shadcn init のように、雛形ファイルをまとめて書き出すコマンド。問いカード = 下の「決めてほしいこと」の各問。お任せ = 未回答のまま送ると推奨案で進めること。例題 = 依頼文の「カウンター (+1 / リセット / 大きなデジタル数字) の 1 ページアプリ」2 本。

決めてほしいこと (4 問 — 未回答は推奨で進める)

問 1. packages の並べ方は、フラットとネストのどちらにしますか?

  • A. フラット推奨 — 利点: 依頼文の「汎用の共有コードは packages/ライブラリ名」に合い、別アプリが ui-components を使っても名前に違和感がない。代償: カウンター専用かどうかが、ディレクトリ名からは分からない。
  • B. ネスト — 利点: カウンター関連が 1 か所にまとまり、アプリが増えても packages/ 直下が散らからない。import 名は @app/counter-ui-components のように接頭辞で区別する。代償: 共有したい ui-components や datastore が counter という名前の下に入る。workspaces の glob が packages/*/* の 2 段になる。

根拠: 依頼文のツリー「packages/ - counter / - datastore-indexed-db …」は、datastore-* と ui-components が counter の下に字下げされています。同じツリーの apps 側でも counter-memory-app が counter-indexed-db-app の下に字下げされています。アプリの中にアプリは置けないので、apps 側はフラットと解釈しました。packages 側だけが判断の対象です。

問 2. Kysely / Atlas は、今回どこまで作りますか?

  • A. 基盤だけ推奨 — 利点: 例題 2 本はブラウザ内で完結するので、使わないコードが増えない。SQLite なので Docker が要らない。代償: Kysely を画面から呼ぶ例が無く、DB を保存先として注入する動作は確かめられない。
  • B. 3 つ目のアプリまで — 利点: 「DB / メモリをアプリ側で切り替える」設計を、本物の DB で一度通せる。代償: サーバー処理 (Server Actions) と DB ファイルの扱いが加わり、パッケージが 2 つ、E2E テストが 1 本増える。

根拠: 依頼文「IndexedDB版はカウンタを永続、メモリ版は揮発」。2 本ともブラウザ内で完結し、Kysely を呼ぶ箇所がありません。

問 3. Next.js・shadcn/ui・Storybook の雛形は、生成コマンドで作りますか、手書きしますか?

  • A. 手書きを基本にし、shadcn の部品追加だけ生成コマンド推奨 — 利点: 依頼文の「新規テキストは echo / cat のリダイレクト」に沿い、手順書どおりに打てば毎回同じものができる。代償: 手順書が長くなり、上流の推奨設定が変わっても自動では追従しない。
  • B. 生成コマンドを使い、差分だけ jq や heredoc で直す — 利点: 上流の推奨設定にそのまま乗れて、手順書が短い。代償: 生成物が版ごとに変わるので、手順書と結果がずれやすい。不要なファイルの削除手順も要る。

根拠: 依頼文「新規テキスト作成はechoやcatからのリダイレクト、jsonへの追記はjqを使用する」。create-next-app・storybook init・shadcn init は設定ファイルと依存をまとめて書き出すので、この方針と両立しにくいです (生成物の数は版によって変わるため、実測していません)。

問 4. カウンターの数字は、どちらの見た目にしますか?

  • A. 7 セグメント (DSEG7)推奨 — 利点: 依頼文の「デジタル文字」に最も近い、電卓や時計の見た目。代償: Google Fonts に無いので、npm の dseg からフォントファイルを取り込み、next/font/local で配信する。
  • B. Orbitron — 利点: next/font/google の 1 行で使え、依存が増えない。代償: 「デジタル風」の書体で、7 セグメントの見た目にはならない。

根拠: npm view dseg version license → 0.46.0 / OFL-1.1。Google Fonts には 7 セグメント書体がありません。上の A の絵はフォントの見た目を図形で再現したものです。
